Hospital Infection Prevention and Quality
Improvement Programme
Problem statement for the NavaDhiti proposal to ShikshaLokam: adapting ELEVATE for a state health
programme. This is a representative case used to show how NavaDhiti adapts and implements
ELEVATE; the proposal answers the questions in section 8.



1. The programme
A State Health Quality Mission is launching a 12-month programme across 150 public hospitals in 12
districts. The programme aims to reduce avoidable hospital-acquired infections by improving hygiene
practices, infection-control audits, corrective actions and supervisory follow-up.

The mission wants one digital system to coordinate the improvement programme without becoming a
patient electronic medical record. The system must help facilities assess current practices, create and
execute improvement plans, capture evidence, obtain supervisor validation, arrange expert support and
demonstrate measurable improvement over repeated assessment cycles.

6. Non-functional and governance constraints
    • Organisation and role-based access must prevent users from viewing unauthorised facilities,
         wards or evidence.
    • Every assessment, plan revision, task decision, evidence review and administrative change must
         be attributable and auditable.
    • Offline synchronisation must address duplicates, conflicting updates, media retries and reference-
         data version changes.
    • The pilot must support 15 hospitals and scale to 150 without redesigning service ownership or
         data boundaries.
    • Programme configuration and operational data must be separated across development, test, UAT
         and production environments.
    • The proposed design must include monitoring, backup, recovery, security patching and controlled
         releases.



7. Guiding principle
Do not assume that ELEVATE must meet every requirement. The solution should use ELEVATE where
its capabilities and service boundaries fit, and explicitly place unsuitable responsibilities in external
systems or programme-specific components.

The proposal should validate one high-risk assumption in its design with a focused code or runtime
check. Examples include organisation-scoped access, assessment-to-project orchestration, audit
behaviour, event publication or evidence handling. The proposal should state the validation method,
code or configuration used, observed result, limitations and resulting architecture decision.
