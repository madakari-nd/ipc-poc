ShikshaLokam's own programmes differ from this one. To show how NavaDhiti understands,
adapts and implements ELEVATE, we took a representative state health case and worked it
through end to end, from requirements to a 12-week pilot plan. NavaDhiti's engineers read
the current ELEVATE code and checked the running services, so every statement about
ELEVATE is marked as confirmed in code (CODE), seen on a running ELEVATE (RUNTIME;
shown as OBSERVED in the presentation), an assumption we have adopted, or a check
scheduled in the first three weeks (SPIKE). These are checks of ELEVATE itself, not a prototype
of the proposed solution.

Problem statement
Please read the problem statement first; this proposal answers it. A State Health Quality
Mission is running a 12-month programme to reduce avoidable hospital-acquired infections
across 150 public hospitals in 12 districts, with about 2,500 users in seven roles, intermittent
connectivity, three languages and no patient data, starting with a 12-week pilot in 15
hospitals. The full statement, with actors, journeys, integrations, constraints and the questions
to answer, is here: IPC Programme - Problem Statement (also attached as
IPC_Programme_Problem_Statement.pdf).

1. Executive recommendation
Recommendation. NavaDhiti recommends using ELEVATE as the operational core for
programme structure, facility hierarchy, ward assessments, improvement-plan structure,
offline field capture, expert mentoring and reporting. It should not be used alone. NavaDhiti
adds a thin, programme-owned layer for the responsibilities ELEVATE does not cover or does
not enforce safely: facility- and ward-level access control, task assignment and evidence
verification, multi-level validation, escalation, checklist version governance and an append-
only audit ledger (hash-chained at scale-up).

This is a reuse-first design, not a maximum-reuse design. NavaDhiti's validation work (section 15)
showed that the ELEVATE services must not be exposed directly to end users in this programme. All
client traffic passes a Programme Edge.

1.2 Main gaps in ELEVATE today (each confirmed in code or at runtime; section
15)
     Access control: evidence, submissions and plan targeting are not scoped by facility or
      ward on the server.
     Workflow: no task owner, dependency, evidence requirement, approval, multi-level
      validation or escalation.
     Offline sync: conflicts between devices sharing a download token are not detected; a stale
      device overwrites newer data and replays are accepted (V4).
     Versioning and audit: no checklist versioning; project history stores only user and time.
     Channels: notification is email only; field apps never capture GPS; question content is
      single-language.
     Tokens: all ELEVATE services share one signing secret per environment, so the secret must
      be protected and rotated.

control officer reviews every evidence item and that load grows with every ward. The ELEVATE
ecosystem already has AI services; the ones we use are the orange row of Figure 1.

6.1 Versioning
     Checklists: a published samiksha solution is frozen. A new version is a new solution
      created from the previous one; the catalogue stores version number, solutionId and a
      hash of the question set. The Edge refuses edit calls on published solutions. Old
      submissions remain bound to their own solution, so they still render with their original
      questions.
     Plan templates: project-service copies template and tasks into each project at creation
      (CODE), so later template changes never alter running plans; the catalogue records which
      template version each plan used.
     Reference data: the hierarchy and scope assignments carry an effective-from date and a
      version number sent to devices.

6.2 Audit history
ELEVATE's own history is not sufficient: project updateHistory stores only user and time and is
rewritten on each sync (RUNTIME V4). Every programme decision (assignment, evidence
decision, validation, escalation, version publish, admin change) is written by the Workflow
Service to the audit ledger with before and after hashes. ELEVATE project and observation
events are also appended, so a plan's state can be reconstructed from the ledger.

6.3 Evidence metadata and the patient-data boundary
Evidence metadata holds facility, ward, task or question, uploader, captured-at time, GPS,
device time skew, content hash and review state. No patient name, number, bed label or
clinical field exists in any schema. Free text is limited in length. The boundary is defence-in-
depth, not moderation alone: at capture the app constrains evidence to the audit subject (for

NavaDhiti | Proposal to ShikshaLokam: ELEVATE for the hospital IPC quality-improvement programme
example wall-, station- or register-level photos) with on-screen guidance and a per-submission
no-patient-data declaration; the Evidence service can run server-side image checks (for
example face detection) and hold any positive for review before it is accepted; and a reviewer
can still reject and permanently delete media that shows a patient, with the deletion audited
without keeping the content. Structurally there is no patient field to populate, so the residual
risk is confined to free text and imagery, which these controls target.

8.3 Authentication, idempotency, errors and retries
     Authentication: users sign in with ELEVATE's own login (password, or OTP where the
      tenant enables it) through the Edge, which passes the call to the user service and keeps
      the ELEVATE token server-side. On every call the Edge checks the token and looks up the
      user's facility and ward scope. No separate single sign-on product is added; if the state
      later mandates its identity provider, ELEVATE's own SSO configuration is used (confirmed
      in spike S4). Services use per-environment service accounts; internal-access-token never
      leaves the private network.
     Idempotency: every client write carries an Idempotency-Key (UUID created when the
      record enters the outbox). The Edge stores key, user and response hash for 7 days and
      returns the stored response on replay. This closes the replay gap seen in V4.
     Conflict detection: the Edge stores a per-project version (hash of the last accepted task
      set). A sync built on an older version is refused with 409 and the client re-downloads and
      merges. ELEVATE's own token check is not relied on (V4).
     Event handling: consumers are idempotent on (topic, key, status); failures go to a dead-
      letter topic with alerting; schemas are versioned and validated before publish.
     Errors and retries: clients retry 5xx and timeouts with exponential backoff and jitter (max
      6 attempts, then manual retry); 4xx is not retried and is shown to the user. Calls between

    A10).

schedule depends on the week-3 spikes closing cleanly. To keep the pilot credible the heaviest

12.6 Scale-up decision point
Gate G5 (week 12) is a readiness and adoption gate: wave 1 has been live for about two weeks,
so it decides scale-up to 150 hospitals in district waves of about 25 hospitals per month. It
uses the success criteria in section 13.3. Scale-up adds content, districts and capacity, and
completes the phased items (hash-chained and WORM audit, SMS channel, additional
checklist families); it does not change service ownership or data boundaries. The gate also
decides whether AI shadow mode starts in the first scale-up wave (section 5.3), using the
hardening status of the AI tools and the labelled test set built from pilot officer verdicts (B36).

12.7 Upstream contribution track
The Edge compensates for ELEVATE gaps only until they are fixed upstream. Week 1: private
disclosure of V1, V5b and V6 to the maintainers with the reproduction scripts (B33). Weeks 2-4:
small pull requests for the V1 (signing scoped to the caller), V5b (fail-closed ownership check)
and C8 (server-side scope) fixes, once the maintainers agree (B34). Weeks 4-6: a design
proposal (RFC) for task assignment and review states in project-service, using the self-creation
portal review statuses (C42) as prior art (B35). Each Edge rule names the upstream fix that
retires it; when an ELEVATE release with the fix is adopted and V1-V6 pass without the rule, the
rule is removed, so the Edge shrinks over time towards a route allow-list plus scope injection.

15.3 Limitations
   The running services used released images (3.4.x); the inspected source is the branch head
    listed in section 3, and each finding's code is present at the inspected commit.
   V1 shows the project-service signs a URL for any caller; this is independent of the object
    store used.
   User B's second-organisation membership was provisioned directly; sign-up and login
    used the account APIs.
   V6 is confirmed at the library level; it did not reproduce against the running service in the
    configuration tested, and that runtime negative is itself inconclusive (the control requests
    returned the same 'token missing' response), so the decision to keep the mode off does
    not rely on it.
   Load, long-duration offline and multi-tenant behaviour were not tested; they are covered
    in sections 9 and 13.

15.4 Resulting architecture decisions
   D2 Programme Edge as the only public entry point, with server-side scope, an ownership
    map and a route allow-list (V1, V3, V5b).
   D4 Evidence service for all signing and retrieval; ELEVATE file routes blocked at the Edge
    (V1).
   Edge idempotency and plan-version conflict checks (section 8.3) instead of relying on
    lastDownloadedAt (V4).
   Plans created through importFromLibrary, not the targeted auto-create path (V3).
   D6 ELEVATE stays on native authentication. The Keycloak weakness, like V1 and V5b, will be
    disclosed privately to the maintainers in week 1 of delivery (backlog B33), with these
    scripts as reproduction steps; no upstream contact has been made yet (V6).
